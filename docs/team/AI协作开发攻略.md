# 二批 CAD 图纸适配：AI 协作开发攻略

适用人员：刚接触项目、使用 Codex 或其他 AI 编程工具的开发者。

本团队的目标是让约定的二批图纸按统一流程生成正确的业务结果。开发者负责理解问题、确认图纸含义和核对结果；AI 帮助查代码、分析原因、实现修改和执行检查。AI 说“完成了”不能代替图纸验收。

本攻略是建议采用的团队流程。模块目录、自动回归工具和正式构建说明尚需负责人落实；下文明确区分现有代码与计划建立的机制。

## 1. 先了解我们在做什么

- 近期交付主线：旧版 `Teigha_Learn_Cad720_newVersion`。
- `newDWG` 保留作参考，不同时推进第二套全面重写。
- 当前样本目录有 52 张 DWG、1 张 DXF、2 个 Excel。Excel 是否能作为某张图的参考结果，要由人工确认。
- 输入图纸只读，输出放独立目录。开发中不能修改图纸去迁就算法。
- 输出成功与业务正确分别登记；缺项、错配、多余项、歧义都要记录。
- 未验证的器件连接关系不能直接输出为确定结果。无法识别应给出问题和来源，不能默默跳过。

每个人先能解释自己模块的“输入是什么、输出是什么、怎样证明正确”，再开始改代码。不要求先读完整个项目。

## 2. 团队分工和修改边界

| 人员 | 主责 | 交付结果 |
| --- | --- | --- |
| 负责人 | 公共 CAD 读取、状态管理、界面接入、统一模板、集成和全图验收 | 可运行的统一版本、回归清单 |
| 线束 A | 表格/文字、接插件、孔位提取 | 有原图来源的结构化数据 |
| 线束 B | 连接关系、分支、长度、线束矩阵数据 | 可核对的关系与长度结果 |
| 电气 A | 保险、器件、端子、名称识别 | 有原图来源的器件和端口数据 |
| 电气 B | 连通关系、供电/接地路径、电气矩阵数据 | 可核对的路径与业务结果 |

两组各自交叉复核。两位负责关系分析的同学与负责人对接导出，Excel 模板和公共导出入口统一维护。

现有业务集中在 `TeighaBase.cs`，约 1.6 万行。先由负责人安排函数范围与接入位置；不要四个人同时让 AI 重构整个文件。

建议逐步建立 `Electrical`、`Harness`、`Export`、`Diagnostics` 等模块边界。这些是规划，不是已经存在的模块。新增模块要有实际按钮或处理流程调用，不能只增加一批没有接入的类。

同一文件的不同函数可以协作，但任务卡必须列明修改范围；公共读取、共享模型、模板、工程配置的改动应提前协调。首次接入可以由负责人完成，避免相互覆盖。

## 3. 第一、二天：环境和一张图的完整流程

### 3.1 使用自己的工作副本

仓库建立后，每人克隆一份到自己电脑，例如 `D:\dev\cad-legacy`。不要让多人或多个 AI 会话同时修改同一个工作目录。同一个人需要并行做多个任务时，使用隔离的工作副本或工作树。

新同学可以使用 GitHub Desktop 管理克隆、分支、提交和 PR；下面的命令行流程表达同一套规则。

### 3.2 打开正确的解决方案

从仓库根目录打开：

`DWG.Development.sln`（旧解决方案为 `Teigha_Learn_Cad\Teigha_Learn_Cad.sln`）

现有主要位置：

| 文件/目录 | 阅读目的 |
| --- | --- |
| `Teigha_Learn_Cad/Teigha_Learn_Cad/Program.cs` | 程序从 `MainForms` 启动 |
| `Teigha_Learn_Cad/Teigha_Learn_Cad/MainForms.cs` | 按钮入口、分析调度、部分 Excel 导出 |
| `Teigha_Learn_Cad/Teigha_Learn_Cad/SingleCAD.cs` | 单图加载和页签处理 |
| `Teigha_Learn_Cad/Teigha_Learn_Cad/TeighaBase.cs` | 图纸读取、选择和大量业务算法 |
| `Teigha_Learn_Cad/TeighaCad_Bll` | CAD 支撑代码 |
| `vendor/runtime`、`vendor/templates`、`app` | 随仓库提供的依赖、模板及已编译程序 |

搜索线束入口可以从 `toxianshuToolStripMenuItem_Click` 开始；接地相关入口可以从 `ClassifyEntities` 开始。这只是查找线索，要继续核实实际按钮调用和输出链路。

### 3.3 使用仓库提供的启动与构建入口

依赖已归档到 `vendor/runtime`，模板在 `vendor/templates`；`app` 包含当前源码构建的程序快照。以项目根目录 README 和 DEPENDENCIES.md 为当前操作依据。

- 只体验软件：双击 `启动软件.cmd`，不需要 Visual Studio 或在线 NuGet 还原。
- 修改源码后：双击 `编译并启动.cmd`，它构建并运行最新源码，而非预编译快照。
- 运行需要 64 位 Windows、.NET Framework 4.x 和 VC2008 SP1 x64 系统运行环境；缺少 VC2008 时启动脚本给出官方安装地址。
- 编译需要 Visual Studio / Build Tools、.NET 桌面组件及 v4.0 目标框架引用程序集。应用和 CAD 库已固定 x64，兼容现有 AMD64 Teigha。
- `ClassLibrary1` 已改为项目引用，不再依赖本机预先构建的 Debug DLL。
- 不升级框架或 CAD SDK。工程新增文件仍需核实加入 `Compile` 项。
- 使用 `DWG.Development.sln` 开发，它不含安装包项目；旧解决方案继续保留。
- 自检使用 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start.ps1 -Build -Check`，不代替实图业务验收。

### 3.4 上手完成标准

每人用同一张负责人指定的样例图完成：启动 → 打开 → 分析 → 导出 → 打开结果核对。

记录源码版本、构建配置、实际 exe 路径、操作步骤、输出路径和结果。确认启动的是刚构建的程序，避免测试到旧 exe。

如果基线也失败，先记录为环境或原有问题。不要把环境错误混入自己的业务修复。

## 4. 第一个任务：只修一个可验证的问题

合适的任务例子：

- 某类线束表中合并单元格导致孔位漏提取。
- 某类器件文字在嵌套块中，现有规则没有读取。
- 某类端点接近但未正确匹配，需要验证容差规则。
- 分析第二张图时混入第一张图结果，需要隔离或清理状态。

不合适的任务描述：“优化线束算法”“完善电气分析”“让所有图都适配”。这些可以是阶段目标，不能直接作为一个新人开发任务。

从 [任务卡模板](任务卡模板.md) 建立任务，至少包含图纸、操作、实际结果、人工期望、允许改动范围、验证样本。具体器件编号和期望值必须来自实际图纸，不能让 AI 编造。

负责人按制图样式与失败原因归类，再选代表图。第一轮宜安排低依赖的小任务，复杂供电/接地路径待基础识别稳定后推进。

## 5. 每个任务固定执行这八步

### 第一步：同步代码，创建任务分支

以下命令只在仓库建立、克隆完成后执行。例子中的分支编号要换成实际任务。

```powershell
git status
git switch main
git pull --ff-only
git switch -c fix/H-001-pin-extraction
```

开始前工作区应干净。已有修改时先辨明所属任务并保存，不要执行 `reset --hard` 或让 AI 删除文件来“清理环境”。同步失败或分支冲突时保留现场，核实原因。

### 第二步：先在旧代码上复现

保存修改前的输出、截图及日志。写下精确操作，涉及选择起点、图层、区域时也要记录。只说“这张图不对”无法复现。

截图适合指出目标位置，不能代替 DWG/DXF 数据与业务基准。表格结果应按约定字段逐项核对。

### 第三步：让 AI 定位处理链路

先让 AI 只读定位。它应指出：按钮/事件入口 → 图元或表格提取 → 识别/匹配 → 关系分析 → 导出。

要求 AI 给出具体文件、函数、代码证据、可能原因及验证方法。检查调用链是否真的使用该函数，避免修到备份代码或未接入入口。

### 第四步：确认最小修改方案

你应能用自己的话说明：“原规则为何失败，新规则增加什么条件，哪些情况不能匹配”。不了解就继续让 AI 解释，并向同组同学或负责人核实业务含义。

涉及接点语义、跨页引用、器件内部导通、继电器状态、长度单位等问题，依据图纸规范或负责人确认的规则处理。AI 的常识推测不能直接作为项目规则。

### 第五步：让 AI 实现并接入

限定本次任务范围，保持现有输出字段和入口兼容。不要顺带格式化整个文件、替换 UI、升级依赖或重写整个模块。

本项目使用传统 `.csproj`，新增 `.cs` 文件必须核实加入了 `Compile` 项。主文件需要最小接入修改时，在任务范围中说明。

一张图中的坐标可以用于定位测试对象，不能把该坐标或文件名写进通用识别逻辑。制图差异可通过有证据的配置处理，并明确配置适用范围。

### 第六步：构建并验证

具体标准见 [验证与提交清单](验证与提交清单.md)。至少检查原失败样本、相似样式、不同样式及容易误匹配的反例；样本可兼具多个作用，不必机械凑数。

改动拓扑或识别规则时，应补能够覆盖错误条件的必要测试。AI 无法操作图形界面或缺少运行库时，开发者自己运行并保存证据；报告应写“尚未运行/待人工验证”。

### 第七步：看 diff，进行复核

先自己检查，再请 AI 做一次只读审查。复核重点：是否错连器件、吞异常、硬编码样本、串用全局状态、改坏字段含义、只添加了未被调用的代码。

另一位同学按相同操作复现。换一个 AI 会话审查可以减少对实现过程的依赖，但不能代替人工业务核对。

### 第八步：提交 PR，由负责人合并

```powershell
git status
git diff --stat
git diff
```

确认后只暂存本次相关文件。可用 GitHub Desktop 逐项选择，也可使用 `git add` 指定具体文件；初期避免不检查就 `git add .`。

```powershell
git commit -m "fix(harness): 修复任务 H-001 的孔位提取问题"
git push -u origin fix/H-001-pin-extraction
```

使用 [PR 模板](PR提交模板.md) 向 `main` 提交 PR。未完成的工作使用草稿 PR。师弟不自行合并主线。

分支落后时，先保存本地修改，再拉取远程主线并合并到任务分支；通过 GitHub Desktop 或 `git fetch origin`、`git merge origin/main` 操作。冲突逐段核对两边业务意图，不允许整文件选择“用我的”或“用对方的”来省事。解决冲突后重新验证受影响部分。

负责人合并后执行全图回归；发现退化时登记、修复或回退相应提交。任务验收依赖合并后的结果，而不仅是开发者分支上的演示。

## 6. 可以直接复制的 AI 提问模板

OpenAI 官方建议提供目标、上下文、约束和完成条件，复杂任务先明确方案，再执行验证。本节按本项目需求展开，而非官方规定的固定流程。[官方最佳实践](https://learn.chatgpt.com/guides/best-practices)

### 模板 A：首次认识自己负责的模块

```text
我刚接触此项目，负责【电气识别/电气关系/线束提取/线束关系】。
请先只读分析，暂不修改代码。
阅读团队攻略及可用项目说明，确认项目根目录。
围绕我的模块查找实际按钮入口、关键函数、数据结构、共享状态和导出位置。
给出一条简洁调用链，并说明输入、输出和可验证方式。
指出环境说明里尚未确认的事项，不要虚构已经存在的测试工具。
```

### 模板 B：定位一个具体错误

```text
任务编号：【编号】。当前分支：【分支】。
图纸：【本机绝对路径】；目标区域：【坐标/截图/图元来源】。
操作步骤：【完整步骤，含起点和图层】。
实际结果：【输出路径、错误字段、日志】。
人工期望：【正确值和图纸依据；不确定项明确列出】。
参考结果：【文件路径及对应行；没有则说明没有】。
请先复现并定位，不修改代码。
说明涉及的文件/函数、已证实原因、待验证假设和最小修复方案。
如果无法运行，请明确缺什么，并给出我可以执行的复现步骤。
```

### 模板 C：开始实现

```text
按已确认的方案完成任务【编号】。
允许修改：【文件/函数范围，包括必要工程接入】。
约束：输入图纸只读；保持【指定字段/模板/入口】兼容；
不按文件名或固定坐标特判；不扩展到无关重构或依赖升级。
完成条件：【具体业务结果】。
验证样本：【失败图、相似图、不同样式图、反例路径】。
补必要的错误诊断和回归测试，使用已验证的构建方式。
完成后列出修改内容、实际运行的检查、输出证据及未验证项。
```

### 模板 D：只读审查

```text
请审查任务【编号】相对 origin/main 的修改，暂不编辑。
结合任务卡和实际图纸，重点查误连接、漏项、误匹配、全局状态污染、
异常被吞、样本硬编码、工程未接入、输出字段变化和验证缺口。
每个问题提供文件位置、触发条件、影响及建议验证方式。
区分已证实问题与假设；没有运行实图不能宣布业务通过。
```

### 模板 E：被卡住或转交任务

```text
请整理任务【编号】的交接记录：当前分支和提交、复现步骤、相关文件、
已证实事实、尝试过但失败的方法、现有输出、未验证项及下一步。
保留已有修改和原始输入，不继续扩大修改范围。
```

如果反复修改仍无证据表明问题改善，先收集交接记录，找同组同学或负责人共同定位。不要连续让 AI 换算法、加容差直到输出“看起来差不多”。

## 7. 图纸验收具体看什么

电气图重点核对器件/保险编号、端子、所属关系、供电/接地路径，以及分支、交叉、器件边框、跨页引用等是否被正确处理。发现保险不等于证明完整供电路径；导线视觉交叉也不自动证明接通。

线束图重点核对连接器与孔位、线路标号、两端对应关系、分支、线径/颜色、长度来源与单位。提取线路表不等于已经得到物理走线路径。

Excel 重点核对漏行、多行、字段值、模板列位和歧义处理。用约定业务键匹配记录，不能仅按行号比较；不能通过随意去重隐藏真实多连接。只有业务允许时才统一空格、单位或大小写，并保存原值。

默认先检查本任务的代表样本，负责人在合并后的版本执行完整 53 图回归。公共读取、拓扑或输出格式变化应在合并前完成全量检查。工具还未建立时按表人工执行，不能把计划中的自动回归写成已经通过。

## 8. 每天如何同步

每天更新任务卡或 GitHub Issue，写四项即可：

1. 修复了哪个具体问题，关联哪些图纸。
2. 有哪些修改前后证据。
3. 还卡在哪里，需要谁确认什么。
4. 下一步要做什么，有没有公共文件冲突。

进度状态建议统一为：待复现 → 已复现 → 开发中 → 待复核 → 待全图回归 → 已验收；缺业务规则、环境或数据时标记阻塞原因。

不要用“AI 写了很多代码”“提取到更多候选”或“成功生成了 Excel”代表验收进度。

## 9. 首周安排

| 时间 | 新同学完成的事情 | 负责人完成的事情 |
| --- | --- | --- |
| 第 1 天 | 环境、启动、统一样例的分析和导出 | 提供可复现基线及依赖说明 |
| 第 2 天 | 画出本人模块调用链，人工核对一张图 | 明确输出字段、操作流程和修改边界 |
| 第 3 天 | 复现一个小问题，填写任务卡 | 建立全图失败清单，分配代表问题 |
| 第 4 天 | 最小实现、验证、草稿 PR | 协调公共接入，检查任务范围 |
| 第 5 天 | 交叉复核、补证据、完成 PR | 合并并执行全图回归，安排下一轮 |

首次业务核对比追求快速提交重要。第一周形成“每个人都能独立复现、修复、验证一个问题”的能力后，再扩大任务规模。

## 10. 团队统一的 AI 项目说明

建议负责人参考 [AGENTS 示例](AGENTS.example.md)，补齐已经验证的环境、命令和模块边界后，放到仓库根目录并命名为 `AGENTS.md`。该示例当前不会自动充当项目规则。

Codex 支持通过 `AGENTS.md` 提供项目级说明。每位同学开始任务时核实实际加载的规则和工作目录；其他 AI 工具按照其机制加载同样的团队约定。[官方 AGENTS.md 说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

团队说明保持简短，将详细流程链接到本攻略。出现重复错误再增加针对性的规则，避免堆积大量无关指令。

## 11. 发 PR 前最后确认

- 我能说明这次错误的原因和新规则的作用。
- 修改范围与任务卡一致，公共接入已经协调。
- 本次修改确实被程序调用，新文件确实参与编译。
- 原失败样本有修改前后的业务差异证据。
- 相似图、不同样式和必要反例没有发现退化。
- 输出可以定位到原图，缺失或歧义没有被隐藏。
- 同组人员已复核，未验证项明确列出。
- 没有混入图纸原件修改、授权密钥、个人路径或无关构建文件。

无法满足的项目如实登记，提交草稿 PR 寻求协助；完成验证后再申请合并。
